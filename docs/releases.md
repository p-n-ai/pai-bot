# Releases

Every successful `CI` run for a push to `main` starts `Nightly candidate`. The workflow builds each missing application image once, tags it with the full commit SHA, and resolves its immutable registry digest without requiring repository-administration permissions. It also resolves the PostgreSQL image published by the source CI run, or records the current compatible PostgreSQL image under the same SHA when the Dockerfile did not change. The resulting `candidate.json` binds all three image digests to the one-time `nightly-candidate-<sha>` artifact. A rerun reuses the existing artifact, while an interrupted run resumes only missing application images.

To promote a candidate, run `Stable release` from `main` with the successful nightly workflow run ID and a new `vMAJOR.MINOR.PATCH` version. The workflow verifies the nightly artifact and its originating successful `main` CI run, then passes the recorded SHA and image digests to the reusable deploy workflow. Production pulls those exact application and PostgreSQL images through the protected `production` environment. The semantic tag and GitHub Release are created only after deployment succeeds.

Promotion fails before deployment when the version is malformed, an existing tag points to another commit, the candidate metadata is missing or ambiguous, the candidate belongs to another repository, or its source CI run does not match the recorded SHA. Stable promotion never rebuilds application images. If tag creation succeeds but release creation fails, rerunning the same version and candidate safely completes the missing GitHub Release.

Database migrations in a stable candidate must remain backward-compatible with the previously deployed application because automated rollback restores application images, not database state. The pull request risk section must state the coordinated rollout or recovery procedure for any migration that cannot satisfy that constraint.
